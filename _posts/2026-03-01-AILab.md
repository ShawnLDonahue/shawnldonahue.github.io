## Introduction

One of the most practical ways to understand AI security is to stop treating it as a cloud service and start treating it like infrastructure.

Running a local LLM in a home lab forces you to confront the same questions enterprise teams are quietly struggling with:

- Where does data actually go?
- What happens when models are fully offline?
- What are the real performance and security tradeoffs of self-hosting AI?

This setup is not theoretical. It is based on a real homelab environment using older enterprise hardware and lightweight models designed to run under constrained compute conditions.

---

## Why Run a Local LLM at Home?

At a high level, there are three motivations:

### 1. Privacy Control
When you run a model locally:
- prompts never leave your environment
- sensitive data does not traverse external APIs
- you control retention, logging, and storage

This allows experimentation with realistic data without introducing external exposure risk.

---

### 2. Security Testing Sandbox
A local LLM becomes a controlled environment for testing:
- prompt injection behavior
- data leakage through retrieval systems
- tool execution risks (local scripts, APIs, services)
- boundary enforcement between “trusted” and “untrusted” data

This turns the LLM into a **security test harness**, not just an AI tool.

---

### 3. Understanding Real Constraints
Running models locally quickly removes abstraction:

- inference latency becomes visible
- memory pressure becomes immediate
- model selection becomes a tradeoff exercise

These constraints directly influence how AI systems must be secured in enterprise environments.

---

## The Home Lab Architecture (Real Setup)

This environment is built on repurposed enterprise hardware:

### Hardware Layer
- **Server:** : Dell Poweredge R310 
- **Memory:** 16 GB RAM  
- **Storage:** ~250 GB RAID array  
- **CPU:** Older Xeon-class CPU (no GPU acceleration)

This is important because it enforces a hard constraint:
> AI workloads must be CPU-efficient, quantized, and deliberately small.

---

### Virtualization Layer
The host is running:

- **VMware ESXi** (bare-metal hypervisor)
- Multiple virtual machines including:
  - Ubuntu Server (primary AI workload host)
  - Home automation environment

This creates isolation between workloads and allows safe experimentation with AI services and networked systems.

---

### Application Layer
Inside the Ubuntu VM:

- Local LLM runtime 
- Lightweight models (notably **Gemma-class small models**)
- Supporting tooling for prompt testing and API exposure

In parallel:
- Home Assistant OS runs as a separate VM/service for home automation integration testing

---

## Why CPU-Only AI Changes Everything

Without a GPU, the system is incredibly constrained:

### What works well
- Lightweight models (e.g., Gemma 2B–7B class)
- Single-user inference
- Short-context prompt testing
- Security experimentation workloads

### What breaks down
- large models (latency becomes impractical)
- multi-agent orchestration
- high-throughput inference
- real-time response expectations

This is not a limitation in a security context—it is a feature:

> Constraints force better architecture decisions.

## Security Value of This Setup

This lab is not about performance—it is about **control and observability**.

### 1. Data Flow Visibility
Every prompt, response, and tool interaction stays local, making it possible to trace:
- input → model processing → output
- data reuse patterns
- potential leakage paths

---

### 2. Trust Boundary Modeling
You can explicitly define:
- what the model is allowed to access
- what services it can call
- what data sources are trusted

This maps directly to:
- least privilege design
- segmentation strategies
- service isolation models

---

### 3. Safe AI Attack Simulation
Because nothing leaves the environment, you can safely test:
- malicious prompt injection patterns
- data exfiltration attempts via summaries
- tool misuse scenarios
- retrieval poisoning in local datasets

---

## Why This Still Matters in Enterprise Security

This kind of setup mirrors real enterprise risk patterns:

- AI is just another interface into data systems
- most failures occur at integration points
- identity and access controls matter more than model behavior

In practice:

> AI does not create new security categories—it amplifies existing ones.

---

## Closing Thoughts

Running a local LLM on constrained hardware like a Dell PowerEdge R310 forces clarity.

You are no longer abstracting AI behind APIs or vendor guarantees. You are directly responsible for:
- compute limits
- data flow design
- access control boundaries
- system behavior under failure

And that is exactly why this kind of lab is valuable:

> It turns AI security from theory into something you can actually break, observe, and understand.
